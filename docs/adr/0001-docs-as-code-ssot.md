# ADR-0001: المستودع مصدر وحيد للحقيقة، والبوابة تُولَّد منه

- الحالة: مقترح (عُدّل في 2026-11-10: VitePress بدل Starlight)
- التاريخ: 2026-11-10
- مرتبط بـ: D-09

## السياق
المطلوب مرجع شامل واحد للمنفذ والمشرف، فيه المواصفات والجدول الزمني والتقدم حتى نهاية المشروع. وإن كُتبت المواصفات في مكان، والمهام في آخر، والقرارات في محادثات، تضاربت النسخ ولن يعرف أحد أيها المعتمد.

## القرار
1. **المواصفات** ملفات Markdown وYAML وJSON Schema داخل `docs/` في هذا المستودع، تحت Git. الاعتماد (Baseline) يتم بـ tag، مثل `spec-v1.0`، ولا يُعدَّل المعتمد إلا عبر طلب تغيير ودمج مراجَع.
2. **المهام والتقدم** في GitHub Issues وGitHub Projects. كل قصة Issue تشير إلى معرّف متطلبها (`F-xx`)، والمراحل Milestones، والجدول الزمني في عرض Roadmap. والقرار النهائي في الأداة معلّق على D-09.
3. **البوابة** موقع ثابت يُولَّد من المستودع بـ **VitePress**، ويُنشر على GitHub Pages. السبب أن الوثائق تبقى Markdown عاديًا يُقرأ على GitHub كما هو: VitePress يحوّل الروابط النسبية بين ملفات `.md`، ويأخذ العنوان من أول H1 دون frontmatter، ويدعم `dir: 'rtl'` والبحث المحلي، ويقرأ البيانات وقت البناء (data loaders) لصفحة التقدم. والموقع **عرض** للمستودع، لا مكان يُحرَّر فيه.
4. الكود في مستودعات منفصلة (التطبيق، والخادم، واللوحة) لاحقًا. وهذا المستودع للمواصفات والقرارات فقط.

## البدائل المرفوضة
- **Notion أو Confluence للمواصفات**: لا يوجد فيهما اعتماد بنسخة مجمّدة ومراجعة دمج، وينفصلان عن الكود والمهام.
- **تطبيق ويب مخصص لإدارة المشروع**: يعني بناء أداة إدارة مشاريع بدل المنتج نفسه.
- **ملف Excel للمهام**: لا يحتمل التوازي ولا الربط بالكود ولا التاريخ.

## العواقب
- كل تعديل له تاريخ ومراجع وسبب.
- يستطيع المطوّر ربط الـ PR بالقصة وبالمتطلب، فتُبنى مصفوفة التتبع (RTM) آليًا.
- يقرأ المعتمِد والمشرف الوثائق في البوابة، لا في محرر نصوص.
- رُفض Astro Starlight لأنه يشترط frontmatter بعنوان في كل ملف، ويحتاج إضافة لتحويل الروابط النسبية.
