# ADR-0002: قاعدة كود Flutter واحدة، وملف تنفيذي لكل تاجر يُحقن وقت البناء

- الحالة: مقترح
- التاريخ: 2026-11-10
- مرتبط بـ: SPK-13, D-05

## السياق
لكل تاجر تطبيق iOS وأندرويد باسمه ومعرّف حزمته وأيقونته. وإنشاء flavor لكل تاجر في Flutter يحتاج كتلة Gradle وscheme في iOS وأيقونات لكل واحد، ولا يحتمل عشرات أو مئات التجار.

## القرار
1. مشروع Flutter واحد بثلاث بيئات فقط: `dev` و`staging` و`prod`.
2. التاجر يُحقن وقت البناء: يجلب خط البناء `tenant.json` من الخادم (معرّف الحزمة، والاسم بلغتين، ونطاق المتجر، والأعلام)، ثم يولّد الأيقونات بـ `flutter_launcher_icons` والسبلاش بـ `flutter_native_splash`، ويعيد كتابة `PRODUCT_BUNDLE_IDENTIFIER` و`applicationId`، ويمرر الثوابت بـ `--dart-define-from-file`.
3. البناء يُطلق من الخادم عبر API لخدمة CI (Codemagic مقترحة، والقرار النهائي في D-05)، ويُبنى الأسطول كله عند كل إصدار.
4. ما يتغير دون بناء (التخطيط، والهوية اللونية، والخطوط، والسبلاش الداخلي) يأتي من الخادم ([ADR-0006](0006-layouts-in-platform-api.md)). وما يحتاج بناءً هو اسم التطبيق والأيقونة والسبلاش الأصلي.

## البدائل المرفوضة
- **مشروع Flutter لكل تاجر**: ستتباعد النسخ، وكل إصلاح يُكرَّر يدويًا.
- **Flavor لكل تاجر**: يتضخم إعداد Gradle وXcode مع كل تاجر.

## العواقب
- إصلاح واحد يصل إلى كل التجار بإعادة بناء الأسطول.
- أول نسخة لكل تطبيق تُنشأ يدويًا في App Store Connect وPlay Console، لأنه لا API لإنشاء سجل التطبيق.
- يجب أن يبقى الملف التنفيذي صغيرًا: خطان مضمّنان فقط، وبلا فيديو مضمّن.
